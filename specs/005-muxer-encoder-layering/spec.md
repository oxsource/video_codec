### User Story 1 - 通过统一 muxer 层封装编码输出 (Priority: P1)

应用开发者完成视频编码后，需要把编码出的裸码流（如 Annex-B H.264）封装成容器格式（如 MP4）以得到可播放的文件或可推送的流。开发者希望使用框架提供的一个独立封装层完成转换，而不需要理解容器格式的内部细节（如 ftyp/moov、SPS/PPS extradata、AVCC 转换）。

**Why this priority**: 这是本功能的核心价值——将格式转换从"消费端临时组合"提升为一等分层能力。此前封装逻辑以临时消费者（Mp4Consumer）形式存在于消费端，开发者需要自行组装，且与编码器无明确分层关系。

**Independent Test**: 开发者通过框架 API 把一个编码完成的 H.264 码流送入封装层，得到合法可播放的 MP4 文件；无需任何容器格式领域知识。

**Acceptance Scenarios**:

1. **Given** 一个已编码完成的 H.264 Annex-B 码流，**When** 开发者调用封装层将其封装为 MP4，**Then** 输出的文件能被标准播放器/工具正常识别与播放
2. **Given** 封装层开始接收包，**When** 遇到首个关键帧，**Then** 容器头部正确生成且首个分片包含头部与首帧数据，保证单次交付即可得到可读文件前缀
3. **Given** 封装过程结束，**When** 开发者显式结束封装，**Then** 容器尾部正确写入，输出文件结构完整（含 moov/mdat 等必需 box）

---

### User Story 2 - 不同平台后端提供各自的封装实现 (Priority: P2)

同一应用需要部署在多个平台（如 Android、Linux、macOS/iOS）。开发者希望框架提供一个可替换的封装实现层，使不同平台可以有自己的封装后端（例如基于系统能力或基于第三方库），但对外暴露一致的接口，开发者无需按平台分别编码。

**Why this priority**: 框架已确立"api 抽象 + backend 实现"模式（编码器即如此），通用 `Muxer` 接口沿用该模式可保持架构一致性，并为 Android/Apple 平台利用系统原生封装能力铺路。

**Independent Test**: 在至少两个平台后端上，开发者用同一段调用代码得到行为一致的 MP4 输出；切换后端不影响上层调用代码。

**Acceptance Scenarios**:

1. **Given** 至少两个平台封装后端已实现，**When** 开发者用同一代码路径在两端分别封装同一码流，**Then** 两个输出文件都是合法 MP4 且媒体内容一致
2. **Given** 某一平台无可用封装后端，**When** 开发者请求封装服务，**Then** 框架清晰返回"不支持"，不会产生损坏输出

---

### User Story 3 - 编码器与封装层解耦 (Priority: P3)

开发者希望编码器只负责产生压缩码流（协议无关），容器封装由独立的 muxer 能力完成，二者通过已确立的包传递机制衔接，职责互不渗透。编码器与封装器在 api 中为平级独立的抽象接口（参考 Android MediaCodec 中编码与封装分离的设计）。

**Why this priority**: 明确的分层约束使编码器保持协议无关（不内嵌容器逻辑），封装器保持格式专注（不触碰编码内部），符合框架既有分层原则，也避免上一轮"封装逻辑内嵌进编码器"方案带来的结构破坏。

**Independent Test**: 同一编码器实例既可输出裸码流（无封装层），也可把码流交给封装层输出容器文件；编码器代码路径完全相同。

**Acceptance Scenarios**:

1. **Given** 编码器配置为不启用封装，**When** 编码完成，**Then** 输出为纯裸码流（保持现状行为不变）
2. **Given** 编码器配置为启用封装，**When** 编码进行中，**Then** 编码器自身不承担任何容器格式逻辑，封装由 muxer 层完成

---

### Edge Cases

- 封装层在收到首个关键帧之前就收到数据（无法构造头部）时，如何处理早期非关键帧？
- 编码中途显式结束（不完整码流）时，如何保证输出文件可恢复（分片模式）而不损坏已有内容？
- 容器格式不支持当前编码格式（如把 Opus 音频封装进仅视频容器）时，如何反馈错误？
- 目标写入端不可寻址（流式推送）与可寻址（本地文件）两种场景下，封装行为如何统一？
- 封装失败（如内存不足、写入端错误）时，错误如何以一致语义向上传递而不产生悬挂资源？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供独立于编码器的格式封装层（muxer），其职责是接收已编码的媒体包并输出容器格式字节流，不承担任何压缩编码职责
- **FR-002**: 系统 MUST 支持将视频裸码流封装为 MP4 容器，输出可被标准工具验证为合法文件
- **FR-003**: 系统 MUST 在 api 层定义通用的 `Muxer` 抽象接口，编码器（encoder）与封装器（muxer）为平级独立的抽象；backend 以该接口为实现边界
- **FR-004**: 系统 MUST 允许不同平台以独立后端形式提供封装实现，后端间互不依赖，且对上层暴露一致的封装行为；首个后端为 FFmpeg 系 muxer 实现
- **FR-005**: 编码器 MUST 保持协议无关：同一编码器在不启用封装时输出裸码流，启用封装时由 muxer 层完成格式转换，编码器自身不内嵌容器逻辑
- **FR-006**: 封装层 MUST 支持至少两种字节输出目标（可寻址文件与不可寻址流式目标），且封装逻辑本身不绑定具体写入方式
- **FR-007**: 封装层 MUST 在首个关键帧处一次性产出"容器头部 + 首分片"，保证拉取式（单次取一个包）与推送式（连续投递）两种衔接方式都能得到完整可用的输出前缀
- **FR-008**: 系统 MUST 在请求不支持的输出格式或平台无可用后端时返回明确错误，且不产生损坏输出
- **FR-009**: 现有 `Mp4Muxer`/`Mp4Consumer` 专用封装组合 MUST 随通用 `Muxer` 接口的引入而移除或退化为 backend 内部实现细节，不再作为对外消费端组件暴露

### Key Entities *(include if feature involves data)*

- **封装器抽象（Muxer）**: api 层定义的通用接口，接收已编码媒体包、产出容器字节流；编码器（encoder）与封装器（muxer）平级独立，各自以抽象接口对外
- **容器格式**: 封装器支持的具体容器（v1 聚焦 MP4），定义了头部、分片、尾部等结构约束
- **封装后端**: 特定平台/库对 `Muxer` 接口的实现（首个为 FFmpeg 系 muxer），通过统一的注册/选择机制提供给上层
- **字节输出目标**: 封装器产出字节的最终去向（本地文件、内存缓冲、网络/云流），与封装逻辑解耦
- **媒体包**: 编码器产出的已压缩数据单元（携带时间戳与关键帧标记），是封装器的输入契约

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 开发者调用框架完成"编码 → MP4 封装"全流程所需的新增代码量，相比此前自行组合消费端方案的实现量减少一半以上（默认目标，可在计划阶段校准）
- **SC-002**: 封装后的 MP4 文件 100% 通过标准媒体工具（如播放器/探测工具）的结构与可播放性校验
- **SC-003**: 启用封装后，端到端编码到落盘的总耗时相对裸码流模式增幅不超过 5%（默认目标，可在计划阶段校准；以用户可感知的端到端耗时衡量，而非内部吞吐量）
- **SC-004**: 至少两个平台后端通过同一调用代码产生行为一致的合法输出，无需上层按平台分支

## Assumptions

- 本功能延续框架既有模式：api 层定义抽象接口（如 `VideoEncoder`/`AudioEncoder`），backend 提供平台实现；通用 `Muxer` 接口沿用该模式，不引入全新架构范式
- 参考 Android MediaCodec：编码（encoder）与封装（muxer）为两个独立平级的能力，api 中分别以抽象接口呈现；如 api 命名组织上有必要，可拆分为 encoder 与 muxer 两组接口声明
- v1 聚焦视频 MP4 封装（H.264），首个封装后端为 FFmpeg 系实现；音频封装与更多容器格式不在本功能范围内（后续扩展）
- 现有 `mux/Mp4Muxer`（FFmpeg libavformat 实现）作为第一个封装后端的基础实现，迁移/重构以适配通用 `Muxer` 接口，而非推倒重写；`Mp4Consumer` 对外不再暴露
- 字节输出目标沿用已确立的 io 层契约（如 ByteSink），封装器通过该契约输出，不新造写入抽象
- 编码器默认行为（不启用封装时输出裸码流）必须保持不变，现有测试不因本功能而失败
